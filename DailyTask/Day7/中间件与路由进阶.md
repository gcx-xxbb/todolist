## 路由中间件深入

- 执行顺序控制
  Express应用的核心是一个中间件栈,它遵循先注册,先执行的原则。这意味着中间件在代码中被`app.use()`或路由方法(如`app.get()`)定义的顺序，直接决定了他们处理请求的顺序。
  1. 中间件在路由处理函数之前:这是最常见且正确的做法。将中间件放在路由处理函数之前，可以确保请求在到达业务逻辑前，先经过预处理，如身份验证、日志记录、请求体解析等。
  2. 中间件在路由处理函数之后:如果将本应起作用的中间件错误地放在路由处理函数之后，它将不会对该路由生效。因为请求一旦被路由处理函数通过 `res.send()` 等方式响应，请求-响应周期就结束了，后续的中间件将不会被执行。
- 路由级中间件:`router.use()`与特定路径应用
  当使用`express.Router()`创建路由分组时，中间件的应用方式变得更加灵活，可以精准控制其作用范围
  - 在路由组件内部使用`router.use()`
    在`Router`实例内部使用`router.use()`，该中间件会对这个路由组内的所有路由生效
    在`app.js`种，通过`app.use('api/',apiRouter)`挂载后，无论是访问'api/users'还是'api/posts'，都会被`apiRouter`处理
  - 在应用层为路由组件绑定中间件
    可以在主应用`app `挂载路由组件时,将中间件和路由组一起传入` app.use()`。这种方式可以更清晰的表达中间件是为特定路径前缀服务的，并且可以灵活控制多个中间件的执行顺序
- 错误处理中间件:捕获与传递
  在路由处理函数或普通中间件中，如果发生错误（尤其是异步错误），必须通过 `next(err)` 将错误传递给 Express。Express 会跳过后续所有非错误处理中间件，直接寻找并执行错误处理中间件

## 路由分组与模块化

1. Router对象:` express.Router()`
   可以把` express.Router()`想象成一个迷你应用
   ` express.Router()`创建了一个新的对象，这个对象拥有和` app`几乎一样的能力(可以定义路由，使用中间件)，但它独立存在，最后再挂载到中间件上
   核心作用:
   - 隔离性:在这个` Router`里面定义的逻辑，不会污染其他的` Router`
   - 复用性:一个`Router` 可以被挂载多次，或者作为基础类被继承
2. 模块化组织:按功能拆分
   当api多变时，将所有路由写在一个app文件种是灾难性的。因此需要按照功能进行拆分
   通常会建立一个routes文件夹，并为其中每个功能创建一个文件
3. 路由前缀:` app.use('api/',router)`
   在主文件`app.js`中，把这些分散的模块组装起来
   通过使用`app.use(path,router)`,可以给整个模块添加一个统一的前缀
   为什么要加前缀呢?
   - 版本控制:通常，api会加上`api/v1`这样的前缀，方便未来升级
   - 语义清晰:明确区分这是api接口,而不是前端路由
   - 避免冲突:确保不同模块的路由不会意外重叠
4. 路由分组内的中间件:可以非常方便的给某一组接口统一增加中间件(比如鉴权模块)

   ```js
   //router/admin.js
   const express = require('express');
   const router = express.Router();

   //在这个Router内部使用中间件，意味着访问admin/api/下的任何路由，都必须先经过这个检查
   router.use((req, res, next) => {
     if (req.headers.role === 'admin') {
       next();
     } else {
       res.status(403).send('禁止访问，需要管理员权限');
     }
   });

   //具体的路由
   router.get('/dashboard', (req, res) => {
     res.send('欢迎来到管理员仪表盘');
   });

   module.exports = router;
   ```

## 参数处理进阶

在Express开发中，永远不要相信用户的输入是铁律，参数处理不仅要获取数据，更重要的是清洗、验证和标准化
如果直接使用`req.query`或`req.body`中的数据，容易受到SQL注入，xss攻击或因类型错误而导致应用崩溃

### 路由参数验证，确保身份合法

路由参数(` req.params`)通常用于标识资源ID(如`/user/:id`)虽然看起来是数字，但攻击者可能传入恶意字符串(如`/：id`注入脚本)或非法格式

1. 使用`express-validator`来进行验证

```javascript
const { param, valationResult } = require('express-validator');

//自定义验证规则组
const validateUserId = [
  param('id').isInt({ min: 1 }).withMessage('用户ID必须为正整数'),
  param('version')
    .optional() //可选参数
    .inIn(['v1', 'v2']) //只能是v1,v2
    .withMessage('版本号只能是v1或v2'),
];

app.get('user/:id/:version?', validateUserId, (req, res) => {
  //检查验证结果
  const errors = valationResult(req);
  if (!errors.isEmpty()) {
    return res.status(400).json({ errors: errors.array() });
  }

  //数据安全了
  //注意：express-validator 会自定将已经通过验证的参数做类型转换 比如isInt()会自动将字符串转为数字
  const id = req.params.id;
  res.send(`用户${id}的详细信息`);
});
```

2. 自定义中间件验证
   对于简单的逻辑，或者不想引入重型库时，可以手写中间件

```js
const validateIdMiddleware = (req, res, next) => {
  const id = req.params.id;
  // 简单的正则或类型检查
  if (!/^\d+$/.test(id)) {
    return res.status(400).json({ message: 'ID 格式错误，必须是数字' });
  }
  // 转换为数字，方便后续逻辑使用
  req.params.id = Number(id);
  next();
};

app.get('/products/:id', validateIdMiddleware, (req, res) => {
  // 直接使用 req.params.id，不用担心类型问题
});
```

### 查询参数处理:`req.query`的安全与转换

查询参数`(?keyword=abc&page=2)`通常用于过滤、排序和分页。这里最大的坑是类型陷阱和注入风险

1. 类型转换陷阱
   在Express中，所有的`req.query`参数都是字符串类型
   - `?page=1` -> `req.query.page`是`'1'`字符串
   - `?limit=10` -> `req.query.limit`是`'10'`字符串
     如果直接拿他们去数据库做数字比较，可能会出错（例如 "10" < 2 在字符串比较中是 true，因为 "1" 的 ASCII 码小于 "2"）。

   ```js
   app.get('/posts', (req, res) => {
     // 1. 显式类型转换
     const page = parseInt(req.query.page, 10) || 1; // 默认第1页
     const limit = parseInt(req.query.limit, 10) || 10; // 默认每页10条

     // 2. 范围限制 (防止 DoS 攻击，比如 limit=99999999)
     const safeLimit = Math.min(limit, 100); // 限制最大100条

     // 3. 白名单过滤 (防止非法排序字段导致 SQL 报错)
     const allowedSortFields = ['createdAt', 'views', 'title'];
     const sortBy = allowedSortFields.includes(req.query.sortBy) ? req.query.sortBy : 'createdAt';

     res.json({ page, limit: safeLimit, sortBy });
   });
   ```

2. 使用`Joi`进行复杂查询校验
   对于复杂的筛选器（如电商搜索），推荐使用 Joi 定义 Schema，它能一次性完成验证、转换和默认值填充。

   ```javascript
   const Joi = require('joi');

   const querySchema = Joi.object({
     page: Joi.number().integer().min(1).default(1),
     limit: Joi.number().integer().min(1).max(50).default(10),
     keyword: Joi.string().trim().max(50).allow(''),
     category: Joi.string().valid('electronics', 'books', 'clothing').optional(),
   });

   app.get(
     '/search',
     (req, res, next) => {
       const { error, value } = querySchema.validate(req.query);

       if (error) {
         return res.status(400).json({ message: error.details[0].message });
       }

       // value 是清洗后的数据，类型已自动转换（page 变成了数字）
       req.query = value;
       next();
     },
     (req, res) => {
       // 安全地使用 req.query
       res.send(`搜索关键词：${req.query.keyword}, 页码：${req.query.page}`);
     },
   );
   ```

### 请求体预处理

在处理post/put请求时，数据量通常较大。预处理的目标是：在业务逻辑介入前，把数据变成干净的状态

#### 1. 基础预处理：中间件配置

Express内置了`express.json()`和`express.urlencoded()`,但需要注意配置参数

```javascript
import express from 'express';
const app = express();

//JSON解析
//limit:限制请求体大小，防止内存溢出攻击
app.use(express.json({ limit: '10kb' }));

//2.表单解析
//extended:true 允许使用qs库解析复杂对象(如user[address][city]=BJ)
//extendsed:false 仅使用querystring库解析对象(性能稍好，仅支持简单键值对)
app.use(express.urlencoded({ extended: true, limit: '10kb' }));
```

#### 2.数据清洗与标准化

在处理函数前，先加入一个清洗层

#### 常见清洗操作

- 去除首位空格: 防止`"admin "`这种脏数据
- 转义HTML:防止XSS攻击(如果数据是直接展示在页面上的)
- 统一格式:例如将标签字符串`"a,b,c"`转化为数组`['a','b','c']`

#### 使用 express-validator 的清洗链：

```javascript
const { body, sanitize } = require('express-validator'); // 旧版本有 sanitize，新版本直接用 body 链
app.post(
  '/register',
  [
    body('email')
      .trim() // 去除首尾空格
      .isEmail() // 验证格式
      .normalizeEmail(), // 标准化邮箱（如将 Gmail 用户名转为小写）

    body('username')
      .trim()
      .escape() // 转义 < > & ' " 等字符，防止 XSS
      .isLength({ min: 3 }),

    body('tags')
      .optional()
      .custom(value => {
        // 自定义预处理：如果是字符串，转为数组
        if (typeof value === 'string') {
          req.body.tags = value.split(',').map(t => t.trim());
        }
        return true;
      }),
  ],
  (req, res) => {
    // 此时 req.body 已经是清洗过的“纯净数据”
    // email 已经是标准格式，username 已转义
    console.log(req.body);
    res.send('注册成功');
  },
);
```

###　总结：安全数据流
一个健壮的 Express 应用，数据流应该是这样的：

1. 请求进入 -> 基础中间件 (express.json 解析格式)。
2. 验证中间件 (express-validator / Joi) -> 拦截非法数据，返回 400 错误。
3. 清洗中间件 -> 转换类型 (String to Number)，去除空格，设置默认值。
4. 路由处理函数 -> 只处理业务逻辑，不再关心数据是否合法，因为前面已经保证它是干净的了。
